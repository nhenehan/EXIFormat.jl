Performance (measured 2026-11-05, before JExi 0.2.0)

Measured on 2026-11-05 on an AMD Ryzen 7 7840U, Linux 7.2.6, Julia 1.12.7, with the rexi-interop harness: EXIFormat (then called JExi) e336de8, and rexi b2ab2a8 as a release build with rustc 1.99. Each library times itself in-process: a warm-up of at least 2000 runs and 3 s, then 2000 timed runs. The tables give the median in µs. Schema compilation is not included. The harness's reports/latest.md has the same runs with p10–p90.

rexi's median is at or below EXIFormat's in every cell but P2 S4. EXIFormat's p90 is higher than its median by more than rexi's is, because of garbage-collector pauses.

These changes made the decoder about 2.3× faster than the first working version:

  • The string table's starting layout and the decoder's flat tables are worked out once per GrammarSet. Stream setup went from 0.33 to 0.08 µs, and from 16 to 8 allocations.
  • Strings are decoded straight into a scratch buffer that only grows (one allocation per new value).
  • The bit reader reads whole octets directly.
  • The value table hashes a new value once, and hashes a QNameId by its two numbers instead of by objectid.

These ideas were tried and dropped because they measured slower: hashes stored in value entries, presized vectors, a larger scan limit, and flat (context, local id) maps.

EXIFormat takes 1.2–1.9× rexi's time. Encoding from events (no XML parsing) takes 1.6–5.9 µs (14.3–14.5 on U1), which is 1.2–2.1× rexi's time.

These changes made encoding from XML about 2× faster than the first working version: from 178.5 to about 90 µs summed over the 14 cases, and from 37 to 20 µs on U1.

  • No tree. src/xml/stream.jl walks XML.jl's tokenizer and hands each element's events straight to the encoder. Before, a document became an XML.jl node tree, then an XElement tree, then a list of events. On U1 the tokenizer alone takes 5.5 µs, against 19 µs for the tree route to events.
  • Cached name lookups. Element and attribute names go through a (uri, local) map kept in RuntimeTables. Before, they took a URI scan and a binary search by string compare. Productions and code widths come from the same flat tables the decoder uses.
  • Text. Text waiting to be written sits in a byte buffer that only grows, not an IOBuffer. Whitespace-only text is checked on the bytes, so dropped whitespace makes no String.
  • Characters. write_code_points! reads code points from the UTF-8 bytes and writes up to eight octets at once.
  • Value table. A new value is hashed once (get!), as in the decoder, and the context's list is looked up once.

For many small documents, keep one Decoder and one Encoder, and reset! them for each document instead of building new ones. A reset codec reads and writes the same bits as a new one, with about half the allocations.

Strings added to the value table during a stream are stored once each; a value hit returns the stored String without allocating.

Type stability

JET's report_opt finds no runtime dispatch in the decode loop (next! over the body). The test gate checks this on Julia 1.10 and 1.12. The encoder has runtime dispatch in only two places: the enumeration lookup, which compares values in their text form (as rexi does), and the options-document reader.

Start-up

A PrecompileTools workload (src/precompile.jl) compiles a small schema and encodes and decodes a document in each profile at precompile time. A cold bin/exiformat encode takes about 0.75 s (13 s without the workload). Compiling a test schema takes about 0.1 s.
